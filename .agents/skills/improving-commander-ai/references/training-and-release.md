# 训练、真人反馈与配置发布

本文件保留决策流程。完整 CLI、课程、诊断格式按需查 [训练说明](../../../../autotest/COMMANDER_TRAINING.md) 的对应段落，以及 `train_commander_league.py` 当前实现；不默认读完所有历史训练文档。

## 可复查的起点

从仓库根目录工作，先确认 `build/clang-release/PlantsVsZombies.exe` 和 `resources/ai/cold_storage_policy.json` 实际被使用。记录本次源码提交／未提交差异、EXE 和配置身份；把当前策略原样备份到明确的独立目录并校验哈希。旧策略可以作为参数起点，但修过引擎、评分、能力、课程或陪练后，旧成绩不能当作当前成绩。

已有训练器的 `identity.json`／哈希用于阻止不同实验混档，不是 AI 的技能知识，也不保证策略优秀。指纹不符时新建输出目录，禁止篡改哈希继续复用成绩。`--from-candidate` 用于继承参数后重新实测；是否从零训练应做配对比较，而非先认定旧经验已废弃。

## 先选诊断，再决定训练规模

| 目的 | 入口与解释 |
|---|---|
| 最近新增能力的局部改进 | `train_commander_league.py --curriculum abilities`；先查实际课程覆盖，不把局部课程叫作全章验收 |
| 正常开局、防发育空档 | `openings`／`coached` 课程；兼顾多种合法陪练，不只对一个截图阵型调优 |
| 高库存空转／后期残局 | 相关 `reserves`／`endurance` 片段与正常开局分开报告；成型阵地打不过不自动证明开局策略差 |
| 预测收入远高于实收 | `audit_commander_forecasts.py`；需要隔离后续购买时用 `audit_commander_forecast.py`，注明仍有玩家输入等干扰 |
| 怀疑胜率只依赖一个强兵 | `evaluate_commander_roster_ablation.py` 配对删减选项；不能凭胜局购买过某兵就断言因果 |
| 旧参数是否限制探索 | `train_commander_fresh.py` 的同预算起点对照；最终仍冻结参数后用另一批种子验证 |

先给一轮明确的规模和观察点，再按新证据决定是否继续；不为了延长训练而训练。运行过程中可以检查已完成的场次、轨迹和失败日志。发现异常时停在可恢复边界，修改后换实验目录；不要在同一比较批次中途换陪练或规则后合并成绩。

## 运行方式

- 构建与可见启动依照仓库指南。训练也使用当前桌面可见窗口，依次跑游戏；后台数值搜索与“隐藏整个游戏”是两回事。
- 训练根脚本启用 `muteAudio: true`；普通 AutoTest 默认关闭背景音乐、保留音效。不要为训练改写用户长期音量偏好。
- 训练启动不固定 `-Seed 42`。实验种子可以由熵生成并记录；同一组新旧策略使用相同场景与种子，留出另抽新种子。固定复现种子不是禁止项，也不是训练必须只用一个种子。
- 复用 `autotest/run_commander_batch.ps1` 的可见启动与退出码检查；不要拿这个有自动超时终止的批处理启动器限制主人的自由游玩时长。
- 可从下面的**小轮次示例**调整规模。输出目录必须换成未使用的新名字，不把示例参数当作通用发布标准：

```powershell
python autotest/train_commander_league.py --output build/clang-release/autotest/training/abilities_round_new --curriculum abilities --calibration off --generations 1 --population 3 --seconds 180 --long-seconds 360
```

`--calibration off` 会从候选移除旧校准；只有要隔离校准或当前基线本就没有校准时才这样选。其它开关同理，先读当前策略，不无意间同时更换评分、搜索版本和陪练。

## 如何解释结果

1. **可比较性先于胜率。** 检查退出码、`status.json`、`run.log`、是否真的走学习分支、实际购买和技能使用。单个缺失／崩溃场次不能计成普通输赢。
2. **选优与验收分开。** 训练场选出候选后冻结参数，独立留出做配对对照。看过留出后继续挑参数，则下一轮需新的留出。
3. **卡池分组。** 全陆地、删减池、正式关卡分别看。全池胜利不能证明小池会经营，实验强开全兵种也不能悄悄改正式出怪池；水路专用、召唤专用和不可独立创建者按当前训练注册表处理。
4. **轨迹比单个终局截图更有解释力。** 看真实支出、补给、生产、击杀、玩家返冰、反制冷却、队列、小推车及防线形成的时序。目标是找出造成残局的早期决策，不能只训练如何打已经不可逆的劣势阵地。
5. **区分测试分布。** 预摆阵地、外部补阳光、静态无输入和正常资源开局分别报告。换南瓜后排、灰烬坚果、精英菇、猎工和预算型陪练用于暴露不同缺口，不能给陪练额外资源却仍叫正常对局。
6. **没有区分度就不宣布升级。** 新旧都全胜时，不能只因多训练过或累计得分略高就称为更强。可针对真实问题增加有区分度的对手／场景；无需无期限堆场次。`unchanged_policy` 的空留出不是新一轮验证成功。

读取当前课程的 `gate()` 与 `evaluation.json` 决定门槛，不能在看到结果后降低门槛、改计分或把失败标为通过。该门槛只说明特定测试分布下的证据，不保证真人难度。

## 发布、试玩和真人记录

训练器只生成候选；默认保留当前正式配置，直到收益和回归证据支持替换。发布前重新核对参数有效性、正式关卡资格和当前 EXE／资源，保留可回滚的原文件。主人明确要求试用未过门槛候选时，可按现有机制使用 `userRequestedTrial`，同时保留真实 `validated`／门槛状态，不伪造合格。

真人试玩可从 `autotest/scripts/human_cold_storage_10_1.json` 的 `humanObservation` 入口派生目标关卡，按指南启动交互游戏，让玩家操作；先确认日志确实写出。不要同时运行自动陪练接管这局，也不要假定在此聊天中能持续后台监视。打完按记录复查，不凭截图直接给“学会了／没学会”的结论。

训练目录保存身份、检查点、冻结候选和评估；`build/clang-release/autotest/out/<批次>/` 保存真实游戏结果与日志。整理时仅归档本次明确归属的训练材料，保持证据与候选的对应关系；不要清空普通 AutoTest、用户试玩存档或仍在写入的日志。无需把所有对局复制进长期文档。

交付至少说清：程序是否改了、正式权重是否替换、实际比较范围、未通过的原因、备份／结果位置。通过验证后的 Git 提交推送依照仓库长期授权；本技能不额外扩大权限。
